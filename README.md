# 爆款视频复刻 · 提示词 Agent

上传一条爆款视频，Agent 反推出它的提示词结构；用户换上自己的素材、写自己的台词；
Agent 组装出一份能**直接生成**（一遍成功）的提示词。

## 一、这套代码是怎么长的

```
engine/core/        领域内核 —— 纯 Python，零第三方依赖，可独立测试
  types.py          枚举、置信度公式、溯源
  framework.py      框架契约 v1：Schema 即数据，字段规则单点定义
  positions.py      四类位置 → 三色映射
  phrases.py        约束有效性分级、强约束降级检测、必写维度覆盖
  assembler.py      IR → 提示词，含应用位置溯源与压缩记录
  gates.py          14 项交付闸门
  contracts.py      反推中间表示（视频 → IR 的桥）
  ports.py          Provider 端口（靠 Protocol 定义，实现可替换）

engine/app/         应用层 —— 依赖 core，反向不成立
  config.py         配置（密钥只从环境读）
  store.py          项目持久化
  api.py            HTTP 接口
  pipeline/infer.py 反推编排（六步）
  pipeline/to_ir.py 分析结论 → Framework IR
  providers/        ffmpeg / MiMo / CV 的具体实现

assets/             资产（语料 + 短语库，由脚本从规范文档重建）
web/                前端（React + TS）
scripts/            资产构建与运维脚本
```

### 三条架构纪律

**① 领域内核不依赖任何东西。**
`engine/core` 里没有一次网络调用、没有一次文件 IO（资产路径是装配时注入的）。
所以它能在毫秒级跑完全部单测，也能在没网、没 Key 的机器上验证。

**② Schema 即数据。**
`framework.py` 里的 `FIELDS` 既是字段定义，也是字段级锁定规则、
四类位置标注、应用位置追踪的唯一来源。于是"哪个字段能改"只有一个答案，
改契约只需改一处。

**③ 门禁只判一次，UI 与 API 都过它。**
`framework.can_write()` 是唯一的写入门禁。前端不重复实现规则，
后端也不绕过它 —— 锁定位在两层都写不进去（PRD F2.3）。

### 验证

```bash
# 单测（用替身保证逻辑，秒级完成）
.venv\Scripts\python.exe -m pytest

# 活体冒烟（真端口、真视频、真模型，确认"启动起来真的能用"）

.venv\Scripts\python.exe scripts\benchmark.py --dir 测试素材 --no-llm   # 只测 L0 技术层
```

`benchmark.py` 是 PRD §6.1.5「回归基准」的工程雏形：有了真实视频，
反推引擎的表现才有办法被**测量**而不是靠感觉。
结果写入 `assets/regression/baseline.json`，可直接 diff 比较两次改动。

它能自动测的：技术解析、时长、镜头切分数、ASR 命中率、
结构归纳产出率、字数、闸门阻断分布、必写维度覆盖。
**它测不了的**：景别/站位/运镜与标准答案的逐维度准确率 ——
那需要 17 份样本的原始提示词做 ground truth，目前还没接。

### 实测基线（24 条真实爆款视频）

三次迭代的对比 —— 每一步提升都是靠**批量体检测出来的**，不是靠感觉：

| 指标 | 自研切分 | +PySceneDetect | **+YOLO 人体检测** |
|---|---|---|---|
| 反推成功率 | 24/24 | 24/24 | **24/24** |
| 闸门可交付率 | 24/24 | 19/24 | 19/24 |
| **G13 必写维度告警** | 24 条 | 24 条 | **14 条** ↓10 |
| logline 产出率 | 100% | 92% | **100%** |
| **CV 缺口** | 3 项 | 3 项 | **0 项** |
| 平均镜头数 | 1.21 | 2.17 | 2.17 |
| 平均单条耗时 | 25s | 42s | 35s |
| 平均交付字数 | 775 | 831 | 898 |

**YOLO 带来的实际变化**（肉眼可验证）：

| 视频 | CV 判定 | 是否与肉眼一致 |
|---|---|---|
| 菜市场采访-苏 | 近景（人体高度占 0.92）、1 人、居中 x≈0.50 | ✅ 单人近景口播 |
| 爆款视频AI复刻刘畊宏 | 5 镜景别有变化（中近景/近景/中景）、每镜 2 人、左≈0.32 右≈0.70 | ✅ 双人左右对话 |
| IP户外教学 | 6 镜均近景、2 人、左≈0.26 右≈0.73 | ✅ 双人教学 |

跨镜头站位高度一致（左侧稳定在 0.26~0.32，右侧在 0.70~0.73），
这正是 PRD 要的"站位 ≥95%"该有的表现 —— 几何量测本来就该这么稳。

**G13 从 24 条告警降到 14 条**：景别、站位、人物一致性这几项由 CV 确定性
算出后，必写维度立刻补齐，两条视频已经做到 8/8 全覆盖。

三条读得出来的结论：

- **镜头切分换成 PySceneDetect 后，检出能力显著提升**：
  平均镜头数从 1.21 升到 2.17，正确判为多镜头的从 3 条升到 10 条。
  `爆款视频AI复刻刘畊宏`（9 秒 5 个切镜）从"检出 0"变成"检出 5"。
- **G8 阻断的 5 条是真问题，不是误报**：它们是快切混剪
  （如 9 秒 5 个镜头 = 每镜 1.8 秒），塞进一条提示词模型必然丢细节。
  闸门给的是两个方向的方案：延长目标时长拆条，或合并节拍。
- **G7 是常态告警，不是异常**。它反映的是"这些爆款视频本身信息密度就高"，
  需要用户自己精简创作区；把它当阻断会挡住所有合法提示词。

### 靠批量体检抓出来的四个真 bug

单测发现不了这类问题 —— 它们只在真实素材的真实分布里才暴露：

1. **人物数失控**：一条带练视频被抽出 10 个人物 → 10 张多视图 →
   撞爆 Seedance 2.0 的 9 张配额。修法：过滤群体标签
   （`台下观众`/`8名学员`）+ 人物数上限。
2. **镜头模式与切分数自相矛盾**：7 条"1 个镜头却判 multi_shot"。
   切分数是 CV 算出来的确定事实，模型没有推翻它的依据 ——
   现在统一向 CV 结果收敛（`reconcile_shot_mode`）。
3. **末尾碎片镜头让整条反推失败**：一条视频切出 180ms 的尾巴，
   抽帧时 `-ss` 落到实际帧位置之外，ffmpeg 报错并中断全流程。
   修法：碎片并入前一镜；单帧抽取失败不拖垮整条链路。
4. **单人居中的站位被丢掉**：站位归纳只认"左/右"，而单人成片
   最常见的是"始终居中"。按 PRD 站位是致命级维度，
   不能因为"不左不右"就不写。

## 三、外部依赖与开源对比

### 用了什么

| 依赖 | 用途 | 为什么用它而不是自己写 |
|---|---|---|
| **PySceneDetect** | 镜头切分 | 见下方对比，自研实现在低对比度切镜上会漏检 |
| **ultralytics (YOLO)** | 人体检测 → 景别/站位/人数 | 让 PRD 的"CV 强判断"真正落地，置信度从 VLM(0.70) 升到 CV(0.95) |
| ffmpeg / ffprobe | 技术解析、抽帧、抽音轨 | 时长唯一可信来源；抽帧不必自己解码 |
| MiMo API | 视觉理解 / 语义归纳 / ASR | 自带的 ASR 与视觉能力省掉两套服务 |

领域内核（`engine/core`）**不依赖任何第三方** —— 这条纪律让核心逻辑
能秒级测完、能在没网没 Key 的机器上验证。

两个可选依赖都做了**能力探测与降级**：
没装 PySceneDetect 就退回内置的 ffmpeg 均值切分；没装 ultralytics 就
退回"模型单独判断"。两条路都能跑通，能力差异会体现在 `/api/health` 里。

### 镜头切分：从自研换成 PySceneDetect

自研实现用「全帧 RGB 均值色差」判定切点。它有个**原理性缺陷**：
全帧均值只有**一个数**，两个镜头整体色调相近但内容不同时
（同一间屋换了个人、同一货架换了商品），这个数几乎不变 —— 必然漏切。

实测对比（24 条真实爆款视频）：

| 实现 | 平均镜头数 | 只切出 1 个的条数 |
|---|---|---|
| 自研（全帧均值） | 1.21 | 20/24 |
| PySceneDetect ContentDetector | 1.71 | 17/24 |
| PySceneDetect AdaptiveDetector | **1.96** | **15/24** |

最典型的一条：`爆款视频AI复刻刘畊宏` 9 秒内有 5 个明显切镜，
自研实现检出 **0** 个，PySceneDetect 检出 5 个。

PySceneDetect 的核心是**逐像素 HSV 三通道加权差分**
（`delta_hue` / `delta_sat` / `delta_lum`），能捕捉"整体色调不变但画面内容变了"。

**参数校准踩过的坑（值得记下来）**：

```
自适应 1.0 / min_content 2.0 / min_scene 0.3s
   → 合成低对比度视频三个切点全对，但真实视频被切碎成 22~30 段，
     "镜头"只有 0.3~0.5 秒 —— 把正常镜头运动当成了切镜
自适应 1.5 / min_content 4.0 / min_scene 0.6s  → 真实视频仍 14 段，偏碎
自适应 2.0 / min_content 8.0 / min_scene 1.2s  → 刘畊宏 5、户外教学 3、菜市场 1 ✓
自适应 3.0 / min_content 15.0 / min_scene 1.5s → 刘畊宏 3，开始漏切
```

**教训：合成视频上校准出的激进参数，搬到真实内容上必然过度敏感。**
真实镜头有运动、有曝光变化，合成色块没有。

景别 ≥85% / 站位 ≥95% / 人物计数 ≥95% 从"模型判断"升级为"CV 强判断"，
置信度也会从 `VLM_ALONE`(0.70) 升到 `CV`(0.95)。

### 还该吸收但尚未做的

来自 [viral-video-replicator](https://github.com/dingtom336-gif/viral-video-replicator) 的降级链思路：
它每个失败点都标注"用户还能拿到什么 / 质量损失百分比"。
我们目前只记录降级原因，没给**质量影响评估**。这是值得补的。

## 四、资产是脚本生成的，不是手写的

```
MULTIMODAL / TEMPLATES / PHRASES 等规范文档
        │
        ├─ scripts/ingest_corpus.py   样本归档 + 跨样本覆盖率统计
        └─ scripts/build_phrases.py   句式模板 / 禁止项库 / 维度 / 降级规则
                    ▼
        assets/corpus/manifest.json     assets/phrases/phrases.json
```

**为什么不手写 JSON**：禁止项库与句式模板要求逐字一致（G14 的判据）。
手抄一遍就可能错一个字，而错一个字就毁掉约束强度。
脚本让资产可从规范文档重建，每条还记录来源章节。

覆盖率是**算出来的**，不是抄的。当前 10 份样本的结果：

| 维度 | 覆盖 | 含义 |
|---|---|---|
| 眨眼节拍 / 皮肤质感 / 景别 | 10/10 | 模型默认会做错的地方，必须逐字钉住 |
| 机位 / 运镜 | 10/10 | 画面失控的高风险项 |
| 禁止字幕 / 禁止BGM / 禁臆造道具 | 8/10 | 兜底约束 |
| 情绪 | 7/10 | 与 PRD 的"≥70% 即合理"一致 |

## 五、四个必须知道的工程取舍
### 「不猜」是硬约束，不是口号

低置信度字段**留空**而不是填一个像样的猜测。落地方式：

- `<0.50` → 不填，折叠展示请用户补；
- `0.50~0.70` → 标黄，必须用户确认；
- `≥0.70` → 直接采用。

代价是反推结果看着"不完整"。这是刻意的：猜错会导致后续全链路偏移，
而用户很难发现（PRD 红线 7）。

### CV 层有缺口，代码里写明了

规范要求用光流算运镜、用人体框占比算景别、用检测框算站位。
那需要 OpenCV + 姿态估计/人体检测 —— 当前环境（Python 3.14）装不上。

所以 `providers/cv.py` 的策略是：**能确定性算的认真算，算不了的返回
`unknown` 并登记缺口**，绝不编一个数字冒充 CV 结果。缺失的能力会体现在
`/api/health` 的 `cv.missing` 里，对应维度的置信度自动降档为"模型单独判断"。

接入 OpenCV / YOLO / 外部检测服务后，改 `detect_capabilities()` 打开开关即可，
其余代码不动。

### 台词不做比例切分

MiMo 的 ASR 返回整段文本，**不带词级时间戳**。此时把文本按镜头时长比例切开
是在编造对齐关系，还会切出"你这气色也太好了吧，是 / 不是偷偷做项目啦？"这种半句话。

现在的做法：整段归给**时序重叠最多**的那个镜头，其余留空。
`TranscriptSegment.has_timestamps` 如实标注时间码是真实对齐还是仅由音频时长推导 ——
这个标记缺失过一版，导致同一句台词被复制到每个重叠镜头。

切割交给对齐环节由用户定。

### 压缩是真执行，500 字是建议值不是硬上限

PRD 风险 4 明列「提示词 500 字上限 vs 正文常超 1500 字」。
处理方式分两步：

1. **组装阶段按 §9.2 优先级真压缩**（不是只给建议）：
   画质预设展开句 → 人物一致性长尾 → D5/D6 低频禁止项 → 节拍里的场景散文。
   每一步都记为 `CompressionEntry`，红线 4 禁止静默裁剪。
2. **压完仍超预算就如实报**，闸门 G7 给的是**告警**而非阻断，
   并说明"已压掉多少、还需手动精简多少、从哪里下手"。

为什么是告警：PRD §11 表格把 500 字写成「**建议值**」，
处置列是"压缩并标注，或提示精简"，阻断列里没有 G7。
实测 24 条真实爆款视频压到极限后仍在 650~850 字 ——
因为**永不可裁**的部分（D0+D7 约 227 字、站位、音色、台词）本身就占满了。
把它当硬阻断会挡住所有合法提示词。

## 六、交付闸门（14 项常驻 + G15 条件出现）

`engine/core/gates.py` 是纯函数，逐项给结论 + 可执行修复建议。
有阻断项时 `deliverable = False`，导出时会如实带上判定（红线 10）。

**G15（内容对齐已确认）只在本次用过对齐时出现** ——
不给不用这个功能的用户添噪声。

几个容易忽略的：

| 闸门 | 为什么重要 |
|---|---|
| **G1 句柄解析** | 除 `【】` 残留外，还查"形如 `[xxx]` 但不是 `[图N]`"的未解析引用。实测盲区：改人物名漏同步 `multi_view_ref` 会产出 `[王姐多视图]`，看起来像个正常引用，实际已废 |
| **G8 密度** | `节拍数 ÷ 时长 ≤ 0.27`。把 30 秒内容塞进 15 秒提示词，模型必然丢细节 —— 抽卡的头号原因 |
| **G10 LOCK diff** | 逐字段比对锁定位。实测踩过一个 bug：标量数组被摊平成 `positions[0]`，导致契约里声明的规则永远匹配不上、站位改动漏检 |
| **G13 必写维度** | 审的是**最终提示词**而不是 IR —— IR 里 `blink` 存的是键名 `"5s"`，逐字表述要到组装才展开 |
| **G14 约束强度** | 只体检约束段落。台词里说"你先参考一下我的动作"是正常说话，不是把 `1:1复刻` 降级 |
| **G15 对齐未决** | 存在待确认或无处安放的内容时阻断。未经确认的猜测不许污染交付物 |

### 内容对齐（F6）怎么做的

这曾是链路唯一的**断点**：反推只能把台词按时间归到镜头，
而 MiMo 的 ASR 不给词级时间戳，所以用户得一条条手填。
现在可以**一次粘一整段稿子**，系统自动分派到各位置。

**判据是三层叠加**，与反推里「CV 强判断 + 模型补位」是同一套思路：

| 判据 | 权重 | 为什么需要它 |
|---|---|---|
| 说话人一致 | 0.20 | 最强信号；且把台词放进别人嘴里是**硬错误**，单独加分配惩罚 |
| 文本相似度 | 0.45 | `difflib` 字符级 LCS —— 零依赖、可复现，中文短句够用 |
| 时长适配 | 0.35 | 权重最高：1.2 秒的位置塞 18 字，文字再像也不成立 |

**分配用保序动态规划**，不是逐条贪心。人写稿是按顺序写的，
稿子的第 3 句不可能落到第 1 个位置 —— 这个约束把搜索空间从 n! 降到 n²，
既快又准，且不会出现交叉分配。

**几个被实测逼出来的设计**（都是先做错、再改对）：

- **分配权重 ≠ 展示分数**：展示分数要如实反映匹配质量，
  分配权重还要计入说话人冲突的惩罚，让错配**竞争不过**留空。
- **置信度不套 `compute_confidence` 的乘法公式**：那套是给"反推"用的，
  再乘一遍系数会**双重惩罚**。实测一个明显正确的对齐只拿到 0.54，
  逼用户确认本该确信的事。改成直接映射 `0.35 + 0.65 × score`，
  标定后：完全一致 ≈1.00、高度相似 ≈0.80、弱相似 ≈0.55。
- **没有说话人信息时不给中性分**：中性 0.5 会变成加分漏洞 ——
  实测两份毫无共同点的内容靠它拿到 0.65。现在说话人判据不可用时
  把它的权重让给另两维。

**双向引用位置**（PRD F6.4）落地为：内容块同时记
「在原稿里的字符区间」与「绑定的原片时间码」。
测试直接断言 `raw[char_start:char_end] == content`，确保能跳回原稿。

**未决门禁**（F6.6）落地为闸门 **G15**，只在本次用过对齐时出现 ——
不给不用对齐的用户添噪声。存在待确认或无位置的内容时阻断交付。

实测一个有说服力的案例：9 秒 5 个快切的视频，用户写的台词每句需 2.8 秒
但每个位置只有 1.3 秒。系统把 5 处**全部标为时长超限**并阻断交付，
而不是硬塞进提示词让用户去抽卡 —— 这与 G8 密度告警是同一个根因，
两层都抓到了。

### PRD §7 十条红线的落实方式

| # | 红线 | 落地位置 | 怎么保证 |
|---|---|---|---|
| 1 | 不编造参考素材 | `g1_placeholder_residue` | 未绑定的 `asset_id` 直接阻断交付 |
| 2 | 不改动锁定位 | `framework.can_write` | UI 与 API **两层**都过这个门禁 |
| 3 | 不代写台词 | `to_ir._dialogue_for` | 只搬 ASR 结果；无台词就留空 |
| 4 | 不静默裁剪 | `assembler.CompressionEntry` | 每次压缩都记「丢了什么、为什么、省多少」 |
| 5 | 不臆造人物信息 | `to_ir._fill_persons` | 群体词过滤；拿不到名字就留空 |
| 6 | 输出不留 `【】` | `assembler.HandleResolver` | G1 数量 = 0，且所有引用必须解析成 `[图N]` 句柄 |
| 7 | 不猜 | `types.compute_confidence` | <0.50 留空、0.50~0.70 标黄 |
| 8 | 不混用互斥模式 | `g3_exclusive_modes` | 三选一，混用阻断 |
| 9 | 不超配额交付 | `g2_quota` | 按探测到的模型能力校验 |
| 10 | 不假装能一遍成功 | `GateReport.deliverable` | 未全绿不许标记可交付，导出带判定 |

### 明确未完成

**① F6 内容对齐（5 项，最该补）**

这是当前链路唯一的**断点**：用户拿到的提示词里，台词是空的或只有 ASR 的整段，

- **双向引用位置保留**：同时记「在原稿中的字符位置」与「绑定的原片时间码」，

PRD §6.1.5 要求测「运镜 ≥90% / 站位 ≥95% / 景别 ≥85%」这类逐维度准确率。
`benchmark.py` 现在能测的都测了（切分数、ASR 命中、闸门分布、必写覆盖），

参数写进正文有无副作用、`禁止美化` 是否有效、5 节拍/15 秒是否丢细节 ——
